# 原子性（Atomicity）的適用邊界

> 結論：真原子只存在於純 DB 環節；一旦牽涉現實世界控制（設備、外部系統），就幾乎不可能做成原子。這是結構必然，不是設計取捨。

## 原子性的唯一前提

所有要「一起成功／一起失敗」的動作，都必須在同一個**交易管理者（transaction manager）**的管轄底下。只要有一個動作跳出這個範圍（去呼叫別的系統），就沒有真原子，只剩「看起來像原子」的模擬。

## 什麼情況能真原子

| 情境 | 能原子嗎 | 原因 |
|---|---|---|
| 同一台 DB 內，多張表一起寫 | ✅ | 同一個 SQL transaction 管轄 |
| 同一個 DB + 支援 XA/2PC 的外部資源 | ✅（理論） | 有共同交易協調者，兩邊都支援兩段式提交 |
| 單一程式內、單機檔案／記憶體操作 | ✅（不是分散式） | 根本只有一個系統，無一致性問題 |
| DB + HTTP API（自走車、WMS、ERP） | ❌ | HTTP 沒有交易協調者，對方不會跟你 commit／rollback |
| 兩個不同系統各自的 API | ❌ | 同上 |

**判準**：問對方「你支援 XA 嗎？或能跟我做 2PC 嗎？」現代 HTTP 服務幾乎都答「不」，所以真實世界的答案是「幾乎沒有」。

## 為什麼外部控制做不成原子

跨出資料庫去控制設備（自走車、堆疊機）或呼叫外部服務時：

- 對方沒有交易協調者，不會參與你的 commit／rollback；
- 現實世界的動作**無法 undo** —— 車開出去了就是開出去了，沒有「rollback」這回事。

這是**物理限制**，不是技術問題。

## 不做原子時的替代方案

| 方案 | 概念 | 適用 |
|---|---|---|
| Transactional Outbox | 寫資料 + 寫指令放同一個 DB transaction（這一段是真原子）；執行指令移到交易外，非同步、可重試、最終一致 | 落地端需要強保證，動作可事後補 |
| Saga | 不追求同時成功，定義每一步的補償動作，失敗就倒著補回 | 動作本身可逆或有取消機制 |
| 狀態標記 + 對帳 | 資料先落地標記狀態，動作失敗不 rollback，留著供人工／批次對帳補單 | 單線或低頻、可接受人工介入 |

## 核心共識（Jet 已確認）

1. 真原子的唯一舞台是**同一個 DB 內的多張表**。
2. 一旦碰觸實體世界控制，就只剩「紀錄 + 補償 + 對帳」這套思維。
3. 優先級：**資料一定先落地**（資料掉了難找），動作是衍生結果，漏了可以對帳補齊。
   - 先存 → 再動作：失敗時資料在、動作沒發生 → 代價便宜，可補動作。
   - 先動作 → 再存：失敗時動作發生、資料掉了 → 代價貴，難回溯。
4. 分散式原子性不存在時，選**遺失成本高的一側先做**（即資料側）。
5. 單人單終端單線場景：`Save → 呼叫外部 → 成功 commit / 失敗 rollback` 可以接受，但要加短 timeout + 失敗 log 供對帳。

## 附：鎖競爭的設計層級（併發情境）

| 情境 | 設計 | 複雜度 |
|---|---|---|
| 單人單線 | Save→call→commit／rollback + timeout + log | 低 |
| 多人少量（≤5 終端） | 外部呼叫移出交易 + 取號改獨立號碼表（鎖只落單列） | 中 |
| 真正高併發 | Outbox + background worker + 號碼表 | 高 |

併發下的真正瓶頸常是取號的 `MAX(...) WITH (UPDLOCK, HOLDLOCK)` 全表範圍鎖，而非 INSERT 本身；外部 API 呼叫若放進交易內持鎖數十秒，才是最毒的。
